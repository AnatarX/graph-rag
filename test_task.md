# Тестовое задание: мини-GraphRAG по текстовому корпусу

## Контекст

Направление команды — агенты для работы с большими данными: веб-поиск, графы и поиск по ним, векторизация, кластеризация, работа с LLM через API. Это задание — не проверка знания конкретных фреймворков, а способ посмотреть, как ты декомпозируешь задачу, принимаешь инженерные решения и рассуждаешь про масштаб.

**Ориентировочное время: пара вечеров.** Не нужно делать production, реалтайм и сложную оркестрацию. Цель — рабочий скелет end-to-end + понятные рассуждения. Если чувствуешь, что закапываешься, — срежь угол и опиши это в README.

**Делай через Claude Code.** Руками весь этот скелет писать долго — используй Claude Code (или аналогичный агентный инструмент) для генерации и склейки компонентов. Это часть нашего стека, так что заодно посмотрим, как ты работаешь с агентами: как ставишь задачи, что делегируешь, а что проверяешь и правишь сам. В README пары строк про этот опыт будет достаточно.

## Данные

Возьми готовый текстовый корпус с Kaggle, **50–100 документов достаточно** (больше не нужно — важнее структура, чем объём). Подойдёт что угодно с осмысленными сущностями в тексте, например:

- новостные датасеты (BBC News, AG News, News Category Dataset)
- статьи / абстракты (arXiv, Wikipedia dumps)
- описания фильмов, компаний, товаров

Выбор датасета — на твоё усмотрение, только укажи в README, что взял и почему.

## Что нужно сделать

### 1. Векторизация
Прогони документы через эмбеддинги (через LLM API cloud.ru или любую embedding-модель на выбор). Сохрани векторы.

### 2. Кластеризация
Разбей документы на смысловые группы (KMeans / HDBSCAN / другое). Кратко обоснуй выбор алгоритма и способ определения числа кластеров. Дай каждому кластеру человекочитаемое название (можно через LLM по нескольким репрезентативным документам).

### 3. Граф знаний
Через LLM (cloud.ru) извлеки из документов **сущности** (люди, компании, места, продукты — по ситуации) и **связи** между ними. Построй граф: узлы — сущности, рёбра — отношения (networkx или аналог, ничего тяжёлого).

Реализуй осмысленный поиск по графу, например:
- через какие сущности связаны X и Y (путь между узлами)
- всё, что связано с сущностью X через 1–2 хопа
- какие документы упоминают сущности из кластера N

### 4. Ответ через LLM (cloud.ru)
Функция, которая принимает вопрос на естественном языке, находит релевантный контекст (через векторный поиск и/или подграф сущностей), собирает его и отвечает через LLM cloud.ru. По сути — минимальный GraphRAG.

### 5. Простой чат-UI
Минимальный интерфейс — обычный чат, куда пользователь пишет вопрос и получает ответ от системы (пункт 4). Ничего сложного: Streamlit / Gradio / что угодно лёгкое. Это просто точка входа, не трать на него много времени.

### 6. README с рассуждениями (важно)
Отдельно опиши:
- какие решения принял и почему
- где сознательно срезал углы и что бы доделал при наличии времени
- **что бы делал иначе на 10 млн документов вместо 100** — где узкие места по памяти, скорости, стоимости LLM-вызовов, как бы масштабировал каждый компонент

Этот пункт для нас не менее важен, чем код.

## Формат сдачи

Git-репозиторий (или архив) с кодом, README и инструкцией по запуску. Данные можно не коммитить — достаточно ссылки на датасет и скрипта загрузки.

## Критерии оценки

- **Декомпозиция и архитектура** — насколько чисто задача разбита на компоненты, не дублируют ли они друг друга по смыслу.
- **Обоснованность решений** — выбор алгоритмов и параметров с аргументацией, а не «взял первое попавшееся».
- **Связность системы** — работает ли end-to-end, честно ли граф добавляет ценность поверх векторного поиска.
- **Понимание масштаба** — видит ли кандидат bottleneck'и при росте данных (README).
- **Качество кода** — читаемость, структура, разумные абстракции (production-уровень не требуется).

Рабочий прототип на 100 документах + вменяемый README — отличный результат.
