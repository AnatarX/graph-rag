# Mini-GraphRAG по BBC News

Тестовое задание: скелет GraphRAG на небольшом текстовом датасете. Эмбеддинги, кластеризация,
граф знаний через LLM, гибридный retrieval (вектор + граф), чат-UI. Стек: Python, LLM через
OpenAI-совместимый API, scikit-learn, networkx, Streamlit, uv.

Живой прогон для сдачи сделал на локальной Ollama, а не на cloud.ru, тк баланс ради тестов тратить я не стал, поэтому просто взял другую модель. 
Код не привязан к провайдеру (см. `llm_client.py`), так что вернуться на cloud.ru  просто поправить `.env`,

## Датасет

[BBC News (Kaggle, `yufengdev/bbc-fulltext-and-category`)](https://www.kaggle.com/datasets/yufengdev/bbc-fulltext-and-category).
2225 новостных статей, 5 категорий (business, entertainment, politics, sport, tech). 
Взял конкретно его по двум причинам:
  1. Короткие плотные тексты с явными именованными
сущностями. 
  2. Известная категориальная структура удобна как sanity-check для кластеризации.

Из 2225 статей выбрал **100 документов**

Датасет не коммитится, скачивается скриптом:
```bash
uv run python scripts/download_data.py
```

## Ключевые решения и почему

**Эмбеддинги.** `bge-m3`, вызовы кэшируются на диске по хэшу текста и модели, так что повторные прогоны пайплайна почти бесплатны.

**Кластеризация.** KMeans поверх L2-нормализованных эмбеддингов (после нормализации евклидово
расстояние примерно равно косинусному). Число кластеров не фиксировал под известные 5 категорий
датасета: перебирал `k` в диапазоне [2, 15] и брал тот, где максимален silhouette score. Это
единственная метрика качества кластеризации, которой не нужен ground truth. 
Также я KMeans взял вместо
HDBSCAN, тк на 100 плотных документах после нормализации кластеры получаются примерно сферические, не нужно возиться с чувствительными гиперпараметрами HDBSCAN, и не хочется "шумовых" точек без кластера, ибо для запросов вида "документы кластера N" удобнее полное
разбиение. Название кластера получаю от LLM по 5 ближайшим к центроиду документам.

**Граф знаний.** Один LLM-вызов на документ, не на весь датасет разом. Так контекст короче и
предсказуемее, а источник факта (doc_id) достаётся бесплатно. Запрос строгий JSON:
`{entities: [...], relations: [...]}`. Узлы это сущности, ключ узла — нормализованное имя
(casefold + strip), чтобы "Apple", "apple" и " Apple " схлопывались в один узел; отображаемое
имя берётся как самый частый вариант написания. Сверху ещё токен-эвристика (`_resolve_node_key`
/ `_is_alias_of` в `graph_store.py`): более короткая форма имени схлопывается с более длинной,
если её токены — подмножество токенов длинной и совпадает последний токен (обычно фамилия), так
"Blair", "Tony Blair" и "PM Tony Blair" сойдутся в один узел, а "Michael Howard" не склеится с
"Michael Jackson" (общий только первый токен). Это не embedding-based entity resolution — она бы
поймала и парафразы вроде "the Prime Minister" без общего токена с "Tony Blair" — а дешёвая
токенная эвристика, сознательное упрощение для масштаба в 100 документов. Рёбра направленные,
`subject --predicate--> object`, с doc_ids, откуда они взяты.

Query-хелперы графа (`graph_store.py`), каждый доступен и из кода, и из CLI:
- `shortest_path(x, y)`: путь между двумя сущностями (через неориентированную проекцию графа)
- `k_hop_neighbors(x, hops)`: окрестность сущности, соседи и факты между ними
- `docs_linked_to_cluster(cluster_id, ...)`: документы кластера плюс документы вне кластера,
  до которых можно дойти через общую сущность.

```bash
uv run python -m graph_rag.graph_store path "Tony Blair" "Michael Howard"
uv run python -m graph_rag.graph_store neighbors blair --hops 1
uv run python -m graph_rag.graph_store cluster 0
```

**RAG (`rag.py`).** `retrieve()` объединяет два источника контекста: top-k документов по
косинусной близости эмбеддинга вопроса и если в вопросе явно упомянута сущность из графа
(fuzzy-match через rapidfuzz), её k-hop подграф в виде фактов-триплетов. Документы с косинусной
близостью ниже `MIN_DOC_SCORE` (0.2) отсекаются до применения top-k, чтобы совсем нерелевантные
документы не попадали в промпт только потому, что топ-k почти заполнить нечем; факты графа
обрезаются до `MAX_GRAPH_FACTS_IN_PROMPT` (15), иначе сущность с большим количеством связей
раздувает промпт сильнее самого вопроса. `answer()` собирает оба источника в один промпт с
пометкой происхождения и просит LLM отвечать только по контексту, ссылаясь на реальный doc_id
в квадратных скобках, на языке вопроса. UI показывает и сырые источники (документы + факты
графа), и итоговый ответ, чтобы было видно, действительно ли граф что-то добавил к конкретному
вопросу.

## Как запустить

```bash
# 1. Зависимости
uv sync

# 2. Данные
uv run python scripts/download_data.py

# 3. Конфиг: LLM-провайдер (любой OpenAI-совместимый API, см. .env.example)
cp .env.example .env
# вариант A: cloud.ru, заполнить LLM_API_KEY (или LLM_KEY_ID/LLM_KEY_SECRET)
# вариант B: локальная Ollama, раскомментировать её блок в .env, затем:
ollama pull qwen2.5:7b-instruct && ollama pull qwen2.5:3b-instruct && ollama pull bge-m3
ollama serve &

# 4. Весь пайплайн (ingest -> embeddings -> clustering -> graph)
uv run python -m graph_rag.pipeline build
uv run python -m graph_rag.pipeline status   # что уже посчитано

# 5. Чат
uv run streamlit run app/streamlit_app.py

# 6. Запросы по графу из терминала (см. раздел "Ключевые решения")
uv run python -m graph_rag.graph_store --help

# Тесты (не требуют сети/ключа, синтетические данные)
uv run pytest
```

## Срезанные углы и что бы доделал

- Пайплайн полностью отработал на 100 документах, 34 юнит-теста проходят (`uv run pytest`).
  Число узлов/рёбер графа сознательно не зафиксировано здесь как факт: оно зависит от того,
  какая модель извлекала сущности/связи, и от конкретного прогона — в ревью этого README
  получалось и 88/34, и 1157/798 на разных моделях, порядок величины может различаться в
  10 раз. Вместо чисел в тексте — `pipeline build` в конце шага `graph_store` пишет
  `artifacts/run_metadata.json` (модель chat/embed, дата прогона в UTC, число документов,
  число узлов/рёбер именно этого прогона), это единственный источник, которому стоит верить.
  Конкретный пример цены выбора модели: Qwen изредка "утекает" в китайский на коротких
  вопросах, это известная особенность именно этого семейства моделей, причём воспроизводится
  детерминированно на temperature=0 для конкретного промпта, в зависимости от того, как
  собрался контекст.

- **Контекстное окно на документ ограничено `SNIPPET_CHARS` = 2200 символов** (обрезка по
  границе предложения, не голым срезом посередине слова — см. `_truncate_at_sentence` в
  `rag.py`). Этого достаточно, чтобы покрыть медианную статью корпуса почти целиком, но более
  длинные документы всё равно обрезаются, и модель не увидит их хвост. Полноценного чанкинга
  документа на фрагменты с раздельным эмбеддингом каждого — нет, это по-прежнему нерешённая
  архитектурная задача, просто порог сейчас на порядок мягче, чем был раньше (400 символов),
  и болезненность проблемы соответственно ниже.

- **Графовая часть retrieval работает только на именах собственных из датасета**, то есть
  фактически на латинице. Сущности в графе английские (документы английские), а вопрос с ними сопоставляется строковым fuzzy-match. 
  Вопрос "расскажи про Тони Блэра" кириллицей граф не активирует, система делает обычным векторным поиском. "Расскажи про Tony Blair"
  активирует.
  Правильное решение: матчить вопрос с сущностями по эмбеддингам, а не по строке, заодно
  снимает и проблему транслитерации. В рамках пары вечеров не делал.

- Entity resolution — строковая нормализация (casefold) плюс токенная эвристика склейки
  алиасов с общим последним токеном (см. раздел "Граф знаний" выше и `_is_alias_of` в
  `graph_store.py`), а не embedding-based слияние. Это ловит "Tony Blair" / "blair" /
  "pm tony blair" (общая фамилия, подмножество токенов), но не ловит парафразы без общего
  токена: "Barack Obama" и "the President" в один узел не схлопнутся, "President Obama" и
  "B. Obama" — тоже случай, где эвристика не подстрахует так же надёжно, как embedding-based
  linking.

- Нет ре-ранкинга и дедупликации похожих документов в векторном топ-k.
- Нет весов или уверенности на рёбрах графа, все связи равнозначны, хотя LLM мог извлечь их
  с разной степенью уверенности.

## Масштабирование: 100 документов → 10 миллионов

**Эмбеддинги.** Сейчас синхронные батч-вызовы и .npy целиком в памяти. На 10M документов нужны асинхронные параллельные воркеры и очередь заданий
вместо последовательного цикла. Эмбеддинги стоит хранить не в одном .npy, а в векторной БД например FAISS, Qdrant. brute-force косинус по 10M×1536 float32 (~60GB) в памяти не поместится и не будет O(1).

**Кластеризация.** `KMeans.fit` на 10M векторов в памяти не работает. Варианты: MiniBatchKMeans
с потоковым обучением по батчам, или кластеризовать случайный сэмпл (100k–1M), получить
центроиды и доклассифицировать остальное методом nearest centroid. Подбор `k` через silhouette
тоже не масштабируется (квадрат память на попарные расстояния).

**Извлечение графа.** Главный источник стоимости здесь: LLM-вызов на документ. На 10M
документов это 10M вызовов. Помогло бы: батчинг нескольких документов в один промпт со
структурированным выводом по каждому вместо строго 1:1; дешёвая или fine-tuned NER-модель для
базового извлечения
сущностей, а LLM оставить только на типизацию и связи поверх уже найденного; обязательный
дисковый кэш (уже есть) с инкрементальной обработкой, чтобы новый документ не требовал
пересчёта старых.

**Entity resolution на масштабе.** Строковая нормализация развалится: "Barack Obama",
"President Obama", "B. Obama", разные узлы. Нужен полноценный entity linking: blocking
(группировка кандидатов по префиксу, фонетике, embedding-похожести, чтобы не сравнивать все
пары), embedding-based similarity, возможно связка с внешней базой знаний вроде Wikidata для
канонизации.

**Хранение и запросы графа.** `networkx` в памяти процесса упирается в потолок в районе
единиц-десятков миллионов рёбер, и он однопроцессный. На 10M документов граф знаний легко
перевалит за десятки или сотни миллионов рёбер, нужна graph DB (Neo4j, JanusGraph, Amazon
Neptune) с индексами по типу связи и источнику факта, шардирование, и материализация часто
запрашиваемых k-hop окрестностей заранее.

**RAG на serving-этапе.** Векторный поиск через ANN-индекс, не brute-force. Поиск сущностей в
вопросе не через полный fuzzy-match по всем узлам (O(n) на запрос), а через заранее построенный
текстовый индекс имён и алиасов (inverted index или trie).
