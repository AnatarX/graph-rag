# Mini-GraphRAG

Тестовое задание: скелет GraphRAG на небольшом текстовом датасете. Эмбеддинги, кластеризация,
граф знаний через LLM (с embedding+FAISS+LLM резолюцией сущностей), гибридный retrieval
(вектор + граф), чат-UI. Стек: Python, LLM через OpenAI-совместимый API, scikit-learn, networkx,
faiss-cpu, Streamlit, uv.

Пайплайн не привязан к одному датасету: датасет выбирается настройкой `DATASET`, артефакты
каждого лежат отдельно. Проверено на двух — BBC News и 20 Newsgroups, см. раздел
"Второй датасет".

Живой прогон для сдачи сделал на локальной Ollama, а не на cloud.ru, тк баланс ради тестов тратить я не стал, поэтому просто взял другую модель. 
Код не привязан к провайдеру (см. `llm_client.py`), так что вернуться на cloud.ru  просто поправить `.env`,

## Датасет

[BBC News (Kaggle, `yufengdev/bbc-fulltext-and-category`)](https://www.kaggle.com/datasets/yufengdev/bbc-fulltext-and-category).
2225 новостных статей, 5 категорий (business, entertainment, politics, sport, tech). 
Взял конкретно его по двум причинам:
  1. Короткие плотные тексты с явными именованными
сущностями. 
  2. Известная категориальная структура удобна как sanity-check для кластеризации.

Из 2225 статей выбрал **100 документов**

Датасет не коммитится, скачивается скриптом:
```bash
uv run python scripts/download_data.py
```

### Второй датасет: 20 Newsgroups

Чтобы система не оказалась заточенной под один корпус, тот же пайплайн прогнан на
[20 Newsgroups](https://scikit-learn.org/stable/datasets/real_world.html#newsgroups-dataset)
(идёт со `scikit-learn`, качать вручную ничего не надо). Датасет специально выбран
максимально непохожим на BBC: не новости, а посты Usenet — шумные, с обрывками цитат,
**с нормальным регистром букв** (BBC-корпус целиком в нижнем регистре) и вдвое короче.

```bash
DATASET=20newsgroups N_DOCS=30 uv run python -m graph_rag.pipeline build
DATASET=20newsgroups uv run streamlit run app/streamlit_app.py
```

Что даёт переключение датасета:
- свой каталог артефактов `artifacts/<dataset>/` — графы датасетов не затирают друг друга
  (общим остаётся только `artifacts/llm_cache`, он ключуется по содержимому запроса);
- свой **профиль корпуса** (`corpus_profile.json`), от которого зависят решения пайплайна —
  см. ниже;
- `doc_id` с префиксом датасета (`bbc-0007`, `20newsgroups-0007`).

**Профиль корпуса вместо констант.** Две вещи, подобранные вручную под BBC, теперь считаются
из данных на шаге ingest:
- `has_meaningful_case` — информативен ли регистр букв. У BBC `False` (текст целиком в нижнем
  регистре), у 20 Newsgroups `True`. От этого зависит, применять ли к именам сущностей фильтр
  "в имени должна быть заглавная буква": на BBC он резал бы легитимные `microsoft`/`yukos`
  наравне с мусором, а на 20 Newsgroups это самый дешёвый способ отсечь описательные обороты.
  Разница видна в результате: в графе BBC остаются нарицательные `companies`, `firms`, а в
  графе 20 Newsgroups — почти чистые имена собственные (`Arab Liberation Army`, `Kfar Etzion`,
  `ADCOM GTP-500II`, `UPENN`).
- `median_doc_chars` — медианная длина документа, из неё берётся размер окна контекста
  (`rag.snippet_chars`). BBC — 2137 символов, 20 Newsgroups — 839.

## Ключевые решения и почему

**Эмбеддинги.** `bge-m3`, вызовы кэшируются на диске по хэшу текста и модели, так что повторные прогоны пайплайна почти бесплатны.

**Кластеризация.** KMeans поверх L2-нормализованных эмбеддингов (после нормализации евклидово
расстояние примерно равно косинусному). Число кластеров не фиксировал под известные 5 категорий
датасета: перебирал `k` в диапазоне [2, 15] и брал тот, где максимален silhouette score. Это
единственная метрика качества кластеризации, которой не нужен ground truth. 
Также я KMeans взял вместо
HDBSCAN, тк на 100 плотных документах после нормализации кластеры получаются примерно сферические, не нужно возиться с чувствительными гиперпараметрами HDBSCAN, и не хочется "шумовых" точек без кластера, ибо для запросов вида "документы кластера N" удобнее полное
разбиение. Название кластера получаю от LLM по 5 ближайшим к центроиду документам.

**Граф знаний.** Один LLM-вызов на документ, не на весь датасет разом. Так контекст короче и
предсказуемее, а источник факта (doc_id) достаётся бесплатно. Запрос строгий JSON:
`{entities: [...], relations: [...]}`. Узлы это сущности, ключ узла — нормализованное имя
(casefold + strip), чтобы "Apple", "apple" и " Apple " схлопывались в один узел; отображаемое
имя берётся как самый частый вариант написания. Резолюция имён — двухуровневая:

1. Токен-эвристика (`_resolve_node_key`/`_is_alias_of` в `graph_store.py`), бесплатная и быстрая:
   более короткая форма имени схлопывается с более длинной, если её токены — подмножество токенов
   длинной и совпадает последний токен (обычно фамилия), так "Blair", "Tony Blair" и "PM Tony
   Blair" сойдутся в один узел, а "Michael Howard" не склеится с "Michael Jackson" (общий только
   первый токен).
2. Если токен-эвристика не нашла узел — embedding+FAISS+LLM резолюция (`entity_resolution.py`):
   имя новой сущности эмбеддится (bge-m3), top-k ближайших имён уже известных узлов ищутся в
   FAISS-индексе (`IndexFlatIP` по L2-нормализованным векторам), кандидаты выше порога похожести
   проходят blocking-фильтр (см. ниже) и, обогащённые типом, алиасами и парой фактов из графа,
   идут на суд LLM — та же это сущность или нет. Именно этот шаг ловит синонимы без общего
   токена, с которыми токен-эвристика ничего не может сделать: `iaaf` +
   `international association of athletics federations`, `bnp` + `british national party (bnp)`,
   `eu` + `european union`, `amnesty` + `amnesty international`, `britain` + `uk`.

   **Порог отбора кандидатов рыхлый, а блокинг — жёсткий, и это не случайно.** Косинусное
   сходство имён на этом корпусе не разделяет синонимы и разные сущности чисто: у настоящих
   синонимов 0.85+, но шум от заведомо разных сущностей доходит до 0.6-0.65. Поэтому
   `SIMILARITY_THRESHOLD=0.55` (recall), а решение — за LLM. Но отдавать LLM всё подряд нельзя,
   и вот почему — замеры на первом прогоне, когда блокинга ещё не было:

   - **Точность.** В зоне 0.55-0.80 у маленькой локальной модели нет ничего, кроме двух имён,
     и она начинает угадывать. Реальные ложные слияния того прогона: футболист `cisse` слился с
     `nicolas cage` (0.559), `ebell` с `ebay` (0.666), законопроект `bill` с `bush` (0.714),
     `anfield` с `liverpool`. Из 57 слияний ошибочными были около десятка — и это именно
     **именованные** сущности, люди и организации, а не только нарицательный мусор.
   - **Цена.** LLM-суд звался 704 раза на 100 документов и занимал часы на локальной модели —
     дороже всей остальной сборки графа вместе взятой, при 57 полезных слияниях.

   Блокинг (`_worth_asking_llm`) — стандартный для entity resolution дешёвый фильтр перед
   дорогим сравнением: пара доходит до LLM, только если есть поверхностная улика (вложенность
   токенов — `amnesty` в `amnesty international`; аббревиатура — `iaaf` = International
   Association of Athletics Federations) **либо** похожесть настолько высока, что улик не
   требуется (`britain`/`uk` = 0.837). На реальных парах этого корпуса блокинг сохраняет 15 из
   17 верных слияний и останавливает 10 из 13 ложных, а число LLM-вызовов падает примерно в
   пять раз.

   Цена блокинга, честно: теряются верные слияния без единой общей буквы и с умеренной
   похожестью — на этом корпусе так потерялась пара `tories` / `the conservatives` (0.690).
   Порог `HIGH_SIMILARITY` поднять нельзя: при 0.75 отваливаются уже `iaaf` (0.688) и `bnp`
   (0.628) — проверено замером, а не на глаз.

   Итог на сданном артефакте (`artifacts/run_metadata.json`): 841 узел с одной токен-эвристикой
   против 822 с добавленным семантическим шагом — 20 узлов схлопнулось, из них по одному
   ошибочно. Ошибка ровно одна и показательная: `madrid` слился с `real madrid` (город и клуб) —
   похожесть имён 0.854, то есть блокинг тут бессилен по построению, и это чистая ошибка
   модели-судьи. Это и есть остаточный класс: пары с высокой похожестью имён, где решение
   целиком зависит от качества судьи (см. "Срезанные углы").

Рёбра направленные, `subject --predicate--> object`, с doc_ids, откуда они взяты.

Query-хелперы графа (`graph_store.py`), каждый доступен и из кода, и из CLI:
- `shortest_path(x, y)`: путь между двумя сущностями (через неориентированную проекцию графа)
- `k_hop_neighbors(x, hops)`: окрестность сущности, соседи и факты между ними
- `docs_linked_to_cluster(cluster_id, ...)`: документы кластера плюс документы вне кластера,
  до которых можно дойти через общую сущность.

```bash
uv run python -m graph_rag.graph_store path "Tony Blair" "Michael Howard"
uv run python -m graph_rag.graph_store neighbors blair --hops 1
uv run python -m graph_rag.graph_store cluster 0
```

**RAG (`rag.py`).** `retrieve()` объединяет два источника контекста: top-k документов по
косинусной близости эмбеддинга вопроса и если в вопросе явно упомянута сущность из графа
(fuzzy-match через rapidfuzz), её k-hop подграф в виде фактов-триплетов. Документы с косинусной
близостью ниже `MIN_DOC_SCORE` (0.2) отсекаются до применения top-k, чтобы совсем нерелевантные
документы не попадали в промпт только потому, что топ-k почти заполнить нечем; факты графа
обрезаются до `MAX_GRAPH_FACTS_IN_PROMPT` (15), иначе сущность с большим количеством связей
раздувает промпт сильнее самого вопроса. `answer()` собирает оба источника в один промпт с
пометкой происхождения и просит LLM отвечать только по контексту, ссылаясь на реальный doc_id
в квадратных скобках, на языке вопроса. UI показывает и сырые источники (документы + факты
графа), и итоговый ответ, чтобы было видно, действительно ли граф что-то добавил к конкретному
вопросу.

## Как запустить

```bash
# 1. Зависимости
uv sync

# 2. Данные (для DATASET=bbc; для 20newsgroups скачивать вручную нечего — sklearn сам)
uv run python scripts/download_data.py

# 3. Конфиг: LLM-провайдер (любой OpenAI-совместимый API, см. .env.example)
cp .env.example .env
# вариант A: cloud.ru, заполнить LLM_API_KEY (или LLM_KEY_ID/LLM_KEY_SECRET)
# вариант B: локальная Ollama, раскомментировать её блок в .env, затем:
ollama pull qwen2.5:7b-instruct && ollama pull qwen2.5:3b-instruct && ollama pull bge-m3
ollama serve &

# 4. Весь пайплайн (ingest -> embeddings -> clustering -> graph)
uv run python -m graph_rag.pipeline build
uv run python -m graph_rag.pipeline status   # что уже посчитано

# 5. Чат
uv run streamlit run app/streamlit_app.py

# 6. Запросы по графу из терминала (см. раздел "Ключевые решения")
uv run python -m graph_rag.graph_store --help

# 7. Другой датасет — та же команда с DATASET=... (артефакты не пересекаются)
DATASET=20newsgroups N_DOCS=30 uv run python -m graph_rag.pipeline build
DATASET=20newsgroups uv run streamlit run app/streamlit_app.py

# Тесты (не требуют сети/ключа, синтетические данные)
uv run pytest
```

## Срезанные углы и что бы доделал

- Пайплайн полностью отработал на 100 документах, 61 юнит-тест проходит (`uv run pytest`).
  Число узлов/рёбер графа сознательно не зафиксировано здесь как факт: оно зависит от того,
  какая модель извлекала сущности/связи, и от конкретного прогона — в ревью этого README
  получалось и 88/34, и 1157/798 на разных моделях, порядок величины может различаться в
  10 раз. Вместо чисел в тексте — `pipeline build` в конце шага `graph_store` пишет
  `artifacts/run_metadata.json` (модель chat/embed, дата прогона в UTC, число документов,
  число узлов/рёбер именно этого прогона), это единственный источник, которому стоит верить.
  Конкретный пример цены выбора модели: Qwen изредка "утекает" в китайский на коротких
  вопросах, это известная особенность именно этого семейства моделей, причём воспроизводится
  детерминированно на temperature=0 для конкретного промпта, в зависимости от того, как
  собрался контекст.

- **Контекстное окно на документ ограничено `SNIPPET_CHARS` = 2200 символов** (обрезка по
  границе предложения, не голым срезом посередине слова — см. `_truncate_at_sentence` в
  `rag.py`). Этого достаточно, чтобы покрыть медианную статью корпуса почти целиком, но более
  длинные документы всё равно обрезаются, и модель не увидит их хвост. Полноценного чанкинга
  документа на фрагменты с раздельным эмбеддингом каждого — нет, это по-прежнему нерешённая
  архитектурная задача, просто порог сейчас на порядок мягче, чем был раньше (400 символов),
  и болезненность проблемы соответственно ниже.

- **Ollama через `/v1` молча игнорирует свои же опции — на это я напоролся, и это стоило часов.**
  `.env` позволяет задать `LLM_EXTRA_OPTIONS={"num_ctx": 3072, "repeat_penalty": 1.3, ...}`, и
  код честно шлёт их в `extra_body`. Но OpenAI-совместимый эндпоинт Ollama такие поля
  отбрасывает: запрос с `{"options": {"num_predict": 5}}` спокойно генерирует 81 токен
  (проверял напрямую curl'ом). То есть защита от зацикливания (`repeat_penalty`) не
  применялась вообще — и на шумном корпусе 20 Newsgroups модель уходила в повторяющуюся
  генерацию, упиралась в `max_tokens`, после чего срабатывал ретрай с удвоенным лимитом:
  **~2.6 LLM-вызова на документ вместо одного** и ~15 минут на документ. Починено переходом
  на стандартный OpenAI-параметр `frequency_penalty` (`LLM_FREQUENCY_PENALTY`), который
  работает и у Ollama, и у облачных провайдеров; опции самой Ollama задаются только через
  Modelfile — рецепт есть в `.env.example`. Урок в общем виде: "OpenAI-совместимый" не значит
  "принимает всё", и провайдер об отброшенных полях не сообщает.

- **Что осталось датасето-зависимым.** `select_k` перебирает число кластеров до 15, а у
  20 Newsgroups категорий 20 — то есть до истинного числа тем перебор физически не дотягивается
  (на прогоне из 10 документов это неважно, но на полном датасете упрётся). Пороги
  `MIN_DOC_SCORE`, `SIMILARITY_THRESHOLD`, `HIGH_SIMILARITY` подобраны замерами на bge-m3 и
  зависят уже не от датасета, а от модели эмбеддингов: при смене модели их надо перемерять
  тем же способом (распределение косинусных сходств на реальных парах), а не подбирать на глаз.

- **Графовая часть retrieval работает только на именах собственных из датасета**, то есть
  фактически на латинице. Сущности в графе английские (документы английские), а вопрос с ними сопоставляется строковым fuzzy-match. 
  Вопрос "расскажи про Тони Блэра" кириллицей граф не активирует, система делает обычным векторным поиском. "Расскажи про Tony Blair"
  активирует.
  Правильное решение: матчить вопрос с сущностями по эмбеддингам, а не по строке, заодно
  снимает и проблему транслитерации. В рамках пары вечеров не делал.

- **Качество слияний упирается в модель-судью, и на маленькой локальной модели оно неидеально.**
  Блокинг (см. "Граф знаний") убирает большинство ложных слияний, но не превращает 7B-модель в
  надёжного судью: пары с высокой похожестью имён доходят до неё по построению, и там она всё
  ещё ошибается — в сданном графе так слились `madrid` и `real madrid`. Проверять это стоит не
  по числу узлов, а глазами —
  `uv run python -m graph_rag.graph_store neighbors <имя>` и поле `aliases` в `graph.json`
  показывают, что с чем слилось. На более сильной модели-судье (см. `.env.example`, вариант с
  cloud.ru) результат заметно лучше, и это ровно тот параметр, который стоит менять первым.

- Полных парафраз резолюция не ловит в принципе: "Barack Obama" / "the President" — это
  контекстная кореференция без всякой похожести имён, до FAISS-кандидатов такая пара не дойдёт,
  потому что сходство имён ниже порога отбора. Для этого нужен другой механизм — кореференция
  внутри документа на этапе экстракции, а не сравнение имён постфактум.

- Остаточный мусор в сущностях. Величины (`25%`, `£1bn`, `£500m initiative`) отсекаются
  фильтром `is_valid_entity_name`, длинные фразы — тоже, но нарицательные обороты без имени
  собственного (`companies`, `firms`, `both athletes`) фильтром не ловятся: корпус целиком в
  нижнем регистре, поэтому отличить их от настоящих имён (`microsoft`, `yukos`) постфактум
  нечем — только на уровне промпта. Промпт это требует явно, но `artifacts/extractions.json`
  в репозитории собран ДО последней правки промпта, так что в сданном графе такой мусор ещё
  есть; полная переэкстракция (`pipeline build --force`) на локальной модели — это часы, и я
  на неё не пошёл ради воспроизводимости остальных чисел.

- Нет ре-ранкинга и дедупликации похожих документов в векторном топ-k.
- Нет весов или уверенности на рёбрах графа, все связи равнозначны, хотя LLM мог извлечь их
  с разной степенью уверенности.

## Масштабирование: 100 документов → 10 миллионов

**Эмбеддинги.** Сейчас синхронные батч-вызовы и .npy целиком в памяти. На 10M документов нужны асинхронные параллельные воркеры и очередь заданий
вместо последовательного цикла. Эмбеддинги стоит хранить не в одном .npy, а в векторной БД например FAISS, Qdrant. brute-force косинус по 10M×1536 float32 (~60GB) в памяти не поместится и не будет O(1).

**Кластеризация.** `KMeans.fit` на 10M векторов в памяти не работает. Варианты: MiniBatchKMeans
с потоковым обучением по батчам, или кластеризовать случайный сэмпл (100k–1M), получить
центроиды и доклассифицировать остальное методом nearest centroid. Подбор `k` через silhouette
тоже не масштабируется (квадрат память на попарные расстояния).

**Извлечение графа.** Главный источник стоимости здесь: LLM-вызов на документ. На 10M
документов это 10M вызовов. Помогло бы: батчинг нескольких документов в один промпт со
структурированным выводом по каждому вместо строго 1:1; дешёвая или fine-tuned NER-модель для
базового извлечения
сущностей, а LLM оставить только на типизацию и связи поверх уже найденного; обязательный
дисковый кэш (уже есть) с инкрементальной обработкой, чтобы новый документ не требовал
пересчёта старых.

**Entity resolution на масштабе.** Сейчас есть embedding+FAISS+LLM резолюция (см. раздел "Граф
знаний"), но она рассчитана на сотни узлов: `IndexFlatIP` — точный brute-force поиск (линейный
по числу узлов), и LLM-суд вызывается синхронно на каждую новую сущность по отдельности. На 10M
документов оба места упрутся: индекс нужен приближённый (`IndexIVFFlat`/HNSW вместо
`IndexFlatIP`), а LLM-суд — батчить по несколько кандидатов в одном вызове вместо одного, плюс
blocking (группировка кандидатов по префиксу/фонетике до похода в индекс, чтобы не гонять
эмбеддинг каждой новой сущности против всего индекса). Возможна и связка с внешней базой знаний
вроде Wikidata для канонизации вместо (или в дополнение к) LLM-суду.

**Хранение и запросы графа.** `networkx` в памяти процесса упирается в потолок в районе
единиц-десятков миллионов рёбер, и он однопроцессный. На 10M документов граф знаний легко
перевалит за десятки или сотни миллионов рёбер, нужна graph DB (Neo4j, JanusGraph, Amazon
Neptune) с индексами по типу связи и источнику факта, шардирование, и материализация часто
запрашиваемых k-hop окрестностей заранее.

**RAG на serving-этапе.** Векторный поиск через ANN-индекс, не brute-force. Поиск сущностей в
вопросе не через полный fuzzy-match по всем узлам (O(n) на запрос), а через заранее построенный
текстовый индекс имён и алиасов (inverted index или trie).
